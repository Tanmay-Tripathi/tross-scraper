# tross-scraper — LinkedIn Profile API

Give it a LinkedIn profile URL, get the profile back as structured JSON.

**Purely reverse-engineered: no browser, no headless Chrome, no HTML parsing.**
The service authenticates as a real session and calls LinkedIn's private JSON
API directly over HTTP, then unpacks the response itself. There is no browser
automation dependency in `go.mod` and no HTML parser in the codebase — a profile
costs about **1 second** and **30 MB**. [How it works](#approach).

Go (Gin) API with Redis for caching. The response is **config-driven**:
every one of the 21 profile sections can be switched on or off, and nothing is
ever invented — a section with no data comes back as `[]`, a missing field as
`null`, a disabled section not at all.

```bash
curl -X POST https://tross-scraper-api.onrender.com/public/v1/profile \
  -H 'content-type: application/json' \
  -d '{"profileUrl": "https://www.linkedin.com/in/williamhgates/"}'
```

## Setup

**You need:** Go 1.24+ and Docker. That is the whole toolchain — no Node, no
browser, no Chromium download.

```bash
git clone https://github.com/Tanmay-Tripathi/tross-scraper.git
cd tross-scraper

cp config/local.example.yml config/local.yml   # then add your cookies, see below
make up                                        # Redis in Docker
make run                                       # API on http://localhost:4201
```

Check it:

```bash
curl http://localhost:4201/public/v1/health
curl http://localhost:4201/private/v1/health/ready
```

Or the whole stack in Docker: `make stack`.

### Getting the LinkedIn cookies

The API authenticates as a real logged-in user, so it needs two cookies from a
browser session. **Use a throwaway account, not your personal one**, and set that
account to *Settings → Visibility → Profile viewing options → Private mode*
before you start.

> This is a **one-time manual credential copy by a human**, exactly like pasting
> an API key — it is not part of the request path. You open DevTools once; the
> running service never launches, drives or embeds a browser. After the cookies
> are in config or the environment, every scrape is a plain Go HTTP call.

1. Log into LinkedIn in a normal browser window — **not** incognito, whose
   cookies vanish on close.
2. Open DevTools (`F12`, or `Cmd+Opt+I`).
3. **Chrome/Edge:** Application → Storage → Cookies → `https://www.linkedin.com`.
   **Firefox:** Storage → Cookies.
4. Copy **`li_at`** — a long random string. This is the login.
5. Copy **`JSESSIONID`**. DevTools shows it wrapped in double quotes, like
   `"ajax:1234567890"`. **Strip the quotes** — paste only `ajax:1234567890`.
6. Put both in `config/local.yml`:

   ```yaml
   LinkedIn:
     li_at: "AQEDAS…"
     jsessionid: "ajax:1234567890"
   ```

7. **Do not click "Log out"** in that browser — it invalidates `li_at`
   server-side. Just close the tab.

`config/local.yml` is gitignored. Cookies never belong in the repository.

> Why the quotes matter: LinkedIn wants `JSESSIONID` in the `Cookie` header
> **with** quotes and the same value in the `csrf-token` header **without** them.
> Config stores one clean value and the client sends both forms. Getting this
> wrong produces `CSRF check failed`, and it is the single most common way to
> lose an hour here.

Verify the cookies before running anything:

```bash
go run ./cmd/spike https://www.linkedin.com/in/williamhgates/
```

This is the reconnaissance tool. It calls every upstream endpoint, saves the raw
responses to `testdata/fixtures/`, and prints which sections came back. It checks
the session first and stops immediately if the cookies are stale.

## Configuration

Config is YAML, chosen with `-config` (default `./config/local.yml`).

| File | Purpose | Committed |
|---|---|---|
| `config/local.example.yml` | template for local development | yes |
| `config/local.yml` | your local config, with real cookies | **no** |
| `config/production.yml` | deployed config — every secret is a `${VAR}` reference | yes |

Values support `${VAR}` and `${VAR:-default}`, resolved from the environment at
startup. **That is how credentials stay out of this repository**: the committed
file names the variable, the deployment supplies the value.

Config is validated at boot — a missing Redis host or an unknown section name
stops the process rather than surfacing on the first request.

### Sections

```yaml
Sections:
  experience: true
  education: true
  patents: false      # this key will not appear in any response
```

All 21 sections default to on. A name that is not a real section fails at
startup, so `experiance: true` tells you immediately instead of silently
returning nothing.

### Environment variables (used by `config/production.yml`)

| Variable | Required | Default | Purpose |
|---|---|---|---|
| `REDIS_HOST` | yes | — | Redis hostname |
| `LINKEDIN_LI_AT` | yes | — | the `li_at` session cookie |
| `LINKEDIN_JSESSIONID` | yes | — | the `JSESSIONID` value, no quotes |
| `REDIS_PORT` | no | `6379` | Redis port |
| `REDIS_PASSWORD` / `REDIS_USERNAME` | no | empty | Redis auth |
| `REDIS_TLS_ENABLED` | no | `false` | TLS to Redis |
| `PORT` | no | `4201` | HTTP listen port |
| `APP_ENV` | no | `prd` | `local` / `stg` / `uat` / `prd` |
| `LOG_LEVEL` | no | `info` | `debug` / `info` / `warn` / `error` |
| `CORS_ALLOWED_ORIGINS` | no | empty | comma-separated browser origins |
| `LINKEDIN_DAILY_BUDGET` | no | `200` | hard cap on live scrapes per day |
| `LINKEDIN_CACHE_TTL_MINUTES` | no | `360` | how long a profile stays cached |
| `OTLP_EXPORTER_URL` | no | empty | OTLP endpoint; empty disables tracing |

## API documentation

Base URL: `http://localhost:4201`

| Prefix | Access | Notes |
|---|---|---|
| `/public/v1` | unauthenticated | safe to expose |
| `/v1` | intended for auth | same handlers; no auth middleware yet |
| `/private/v1` | internal only | probes; do not route publicly |

### `POST /public/v1/profile`

```json
{
  "profileUrl": "https://www.linkedin.com/in/williamhgates/",
  "sections": { "patents": false },
  "refresh": false
}
```

| Field | Required | Meaning |
|---|---|---|
| `profileUrl` | yes | any normal profile URL — with or without `www`, a country subdomain, a trailing slash, tracking params or a sub-page |
| `sections` | no | overrides the configured default, one section at a time. Omitted sections keep their configured value |
| `refresh` | no | bypasses the cache and forces a live scrape. Still counts against the daily budget |

### Errors

Every failure returns `{ "code", "message" }` at the code's own status.

| Code | HTTP | Meaning |
|---|---|---|
| `PRF01` | 400 | not a LinkedIn member profile URL |
| `PRF02` | 404 | profile missing, private, or invisible to our account |
| `PRF03` | 502 | LinkedIn answered in a shape we cannot parse |
| `PRF04` | 503 | **our LinkedIn session expired** — needs fresh cookies |
| `PRF05` | 429 | LinkedIn is rate limiting us |
| `PRF06` | 400 | unknown section name in `sections` |
| `PRF07` | 429 | our own daily scrape budget is spent |
| `IR01` | 400 | malformed request body |

`PRF04` is deliberately distinct: it is the one failure that needs a human, and
it must never look like a generic 500.

### Health

- `GET /public/v1/health` — liveness. Touches nothing, cheap enough for an uptime monitor.
- `GET /private/v1/health/ready` — readiness. Probes Redis **and the LinkedIn
  session**, returning 503 if one is down, so an expired cookie shows up on a
  dashboard rather than being discovered by a caller. `database` reports
  `disabled` — see [Storage](#storage).
- `GET /metrics` — Prometheus: request counts, latency histogram, in-flight gauge.

### Bruno collection

Runnable examples with assertions live in [`api_collection/`](api_collection/).
Open the folder in [Bruno](https://www.usebruno.com/), pick an environment and
hit Run. `scrape-profile-sections-override` is the interesting one: it proves a
disabled section is *absent* rather than empty.

## Response schema

```json
{
  "code": "00000",
  "message": "success",
  "result": {
    "profile": {
      "identity": { "name": "…", "firstName": "…", "lastName": "…", "pronouns": null },
      "headline": "…",
      "location": "…",
      "industry": "…",
      "about": "…",
      "contactInfo": null,
      "openTo": [],
      "images": { "profilePhoto": "https://…", "backgroundPhoto": null }
    },

    "experience": [ { "title": "…", "company": "…", "period": { "start": "2022-04", "end": null, "present": true }, "media": [] } ],
    "education": [],
    "skills": [],
    "patents": [],

    "meta": {
      "publicId": "williamhgates",
      "cached": false,
      "fetchedAt": "2026-08-27T09:41:00Z",
      "sectionsReturned": ["experience", "education", "…"],
      "sectionsUnavailable": ["patents", "testScores"]
    }
  }
}
```

### The three rules

| Situation | Result |
|---|---|
| enabled, has data | the data |
| enabled, no data | `[]` for a list, `null` for an optional single value |
| disabled | **the key is absent entirely** |

That last distinction is the point of the design: a caller can always tell
"this person has no patents" from "I didn't ask for patents".

`meta.sectionsUnavailable` names every section that was enabled but came back
empty, so an empty array is never ambiguous.

**Dates keep the precision LinkedIn gave.** A year with no month serialises as
`"2022"`, never `"2022-01"` — inventing January would be exactly the fabrication
this API refuses to do. An ongoing role has `"end": null` and `"present": true`.

### The 21 sections

`about` · `contactInfo` · `openTo` · `experience` · `education` · `skills` ·
`featured` · `projects` · `licensesAndCertifications` · `courses` ·
`recommendations` · `volunteerExperience` · `publications` · `patents` ·
`honorsAndAwards` · `testScores` · `languages` · `organizations` · `services` ·
`careerBreaks` · `causes`

The first three are nested under `profile`; the rest are top-level arrays.

## Approach

### LinkedIn's page is a shell

Open a LinkedIn profile and the HTML you receive contains almost no profile data.
The browser loads a shell, then calls LinkedIn's **private internal JSON API** —
internally called **Voyager** — and draws the page from that JSON.

So this API skips the page and calls Voyager directly, the same way the browser
does. **That is the reverse engineering.** Concretely, `GET
/voyager/api/identity/dash/profiles?q=memberIdentity&memberIdentity={publicId}`
with the `FullProfileWithEntities` decoration returns a whole profile in one
response — around 120 KB and 100+ entities.

**Voyager has two generations, and the older one is being switched off.** The
legacy `/identity/profiles/{publicId}/...` routes — `profileView`, the bare
profile, `profileContactInfo` and `skills` — now answer **410 Gone**, route by
route rather than all at once: `recommendations` under the same prefix still
answers 200. Everything the retired routes carried is available from the dash
profile above, except contact info, which no reachable endpoint exposes any more.
`contactInfo` therefore always serialises as `null` and is reported under
`meta.unavailable`.

**No browser is involved at any point.** That is a requirement of this exercise,
and it is also the faster answer:

| | Voyager API (this service) | Headless browser |
|---|---|---|
| Speed | ~1 second | 5–15 seconds |
| Memory | ~30 MB | ~1 GB — will not fit free hosting |
| Output | already structured JSON | HTML we would have to guess at |
| Breaks when | LinkedIn changes its API | LinkedIn changes any CSS class |

Everything about the wire format lives in `pkg/linkedin/voyager`, so a change like
the 410s above moves that package alone. `go run ./cmd/spike <profile-url>` probes
every endpoint independently and prints which still answer and which entity types
came back — that report is how the dash migration was scoped, and it is the first
thing to run when a section goes empty.

### Authenticating

Voyager needs a logged-in session, which is four things on every request:

| What | Value |
|---|---|
| `li_at` cookie | the session — this *is* the login |
| `JSESSIONID` cookie | e.g. `"ajax:1234567890"`, **with** quotes |
| `csrf-token` header | the same value, **without** quotes |
| `x-restli-protocol-version: 2.0.0` | selects the modern response format |

Plus a real browser `user-agent`; Go's default is trivially identifiable.

One cookie jar is reused for the process lifetime — that behaves like one browser
tab, whereas re-authenticating per call looks like a new login every time.

### Unpacking the response

Voyager does not return nested JSON. It returns a **flat** shape:

```
{
  "data":     { …the answer, referring to things by id… },
  "included": [ …every object, in one flat list, each with an "entityUrn"… ]
}
```

`data` points at things by `entityUrn`; the objects themselves all sit in
`included`. So parsing has two steps: **index `included` by `entityUrn`, then
follow the pointers out of `data`.** Everything after that is ordinary mapping.

There is a fallback worth mentioning: if `data` does not list a section but the
entities are in `included` anyway — which happens when LinkedIn changes which
views it populates — the parser scans by entity type instead. Without that, a
harmless upstream change would silently empty a section, which is the worst kind
of failure because nobody notices.

Images are indirect too. A photo arrives as a `rootUrl` plus artifacts at several
sizes; the real URL is `rootUrl` + the largest artifact's path segment. If either
half is missing the field is `null` — never a constructed link that would 404.

### Keeping the blast radius small

Everything specific to LinkedIn's wire format lives in `pkg/linkedin/voyager`.
If LinkedIn changes Voyager, that package is the only thing that moves. Services,
controllers and the response contract do not know LinkedIn exists.

The rule that nothing is fabricated is enforced in exactly one function —
`pkg/mapper.ToProfileResult`. Having a single place makes it checkable rather
than merely intended, and it is covered by tests that assert the three rules
directly.

### Protecting the account

Aggressive scraping gets an account restricted, and a restricted account means a
dead demo. So:

| Guard | What it does |
|---|---|
| Redis cache (6 h) | the same profile is fetched once, not once per request |
| Daily scrape budget | a hard ceiling; refresh requests count against it too |
| One reused session | one cookie jar, like one browser tab |
| Real browser headers | a bare Go client is trivially detectable |
| Small jitter | avoids a perfectly machine-like request rhythm |
| Private viewing mode | reads stay anonymous, so scraped members aren't notified |

**The full profile is cached, then filtered.** Two callers wanting different
sections of the same person cost one scrape, not two.

### Storage

**Redis is the only datastore, and that is deliberate.** This service holds no
relational state — a scrape is fetched, mapped, cached and returned. Redis earns
its place twice over:

| Use | Why Redis |
|---|---|
| Profile cache | a repeat request must not cost a second visit to LinkedIn |
| Daily scrape budget | a self-expiring per-day counter, the guard on the account |

There is no Postgres. Adding a database that nothing queries would mean one more
thing to provision, one more thing to fail at boot, and — on a free tier that
expires managed databases after a month — a live demo that dies on a timer for a
dependency the code never used.

The seam is still there: `pkg/db` keeps the store, and `RepositoryAccess.Db` is a
nil `*db.Store`. Wiring one back in is a change in `cmd/app/app.go` and nowhere
else. Until then readiness reports `"database": {"status": "disabled"}` —
`disabled` rather than `down`, because absent-by-design is not a fault. The same
state the LinkedIn client reports when it runs without cookies.

### Layering

```
route → controller → service → repository / client → Redis / LinkedIn
```

Controllers own HTTP and never see LinkedIn. Services own the use case and never
see a Gin type. The client returns typed application errors, so no layer above it
ever reads an HTTP status code. Conventions are documented in [CLAUDE.md](CLAUDE.md).

## Deployment

The API is a static binary in an Alpine image running as a non-root user. One
service, one Dockerfile, plus a Redis instance.

### Render (blueprint included)

[`render.yaml`](render.yaml) provisions the API and its Redis over HTTPS.

1. Push to GitHub.
2. Render → **New → Blueprint** → select the repo.
3. Set the two secrets on the API service (they are marked `sync: false`, so they
   are never committed): `LINKEDIN_LI_AT`, `LINKEDIN_JSESSIONID`.

That is the whole deploy. Health check path: `/public/v1/health`.

### Any Docker host

```bash
docker build -t tross-scraper .
docker run -p 4201:4201 \
  -e REDIS_HOST=redis-host \
  -e LINKEDIN_LI_AT="AQEDAS…" \
  -e LINKEDIN_JSESSIONID="ajax:1234567890" \
  tross-scraper
```

### Refreshing cookies

When `li_at` expires the API returns `PRF04` and readiness reports
`linkedin: down`. Repeat the DevTools steps, update the environment variable,
restart. No redeploy, about a minute.

## Known limitations

1. **Every call is made *as* the authenticated account.** LinkedIn returns
   exactly what that account would see in a browser — no more. So *"can we scrape
   profile X?"* reduces to *"can our account see profile X?"*

   Reliably available for anyone: name, headline, location, industry, about,
   experience, education, skills, certifications, projects, publications,
   patents, honours, courses, languages, organizations, volunteering.

   Often empty, because LinkedIn restricts them by relationship — **not a parser
   bug**:

   | Field | Why |
   |---|---|
   | `contactInfo` | email and phone are usually shared only with 1st-degree connections who opted in |
   | `openTo` | often shown only to recruiters or connections |
   | `images.profilePhoto` | the member can restrict their photo to connections |
   | `identity.name` | some members display only a surname initial |

   A direct consequence: **the same URL returns different data for different
   accounts.** Results are relative to whoever's cookies are in use, so comparing
   our output against what *you* see on linkedin.com will not match exactly.

2. **Reading a profile is visible to its owner.** We call the endpoint the
   browser uses to render a profile page, so a fetch most likely registers as a
   profile view. Put the scraper account in **Private (anonymous) viewing mode**.
   This is also why it must be a throwaway account.

3. **Cookies expire.** A password change or a security prompt kills the session
   and the API returns `PRF04` until it is refreshed.

4. **`featured`, `services`, `careerBreaks` currently return `[]`.** LinkedIn
   exposes these only through newer endpoints that are not wired up yet. They are
   returned as empty rather than omitted, and `meta.sectionsUnavailable` lists
   them, so the response never implies the profile has none. `causes` is derived
   from volunteering entries, which is the only honest source in this API.

5. **Voyager is private and undocumented.** LinkedIn can change it without
   warning. The quarantined package limits the damage, but a change means a fix.

6. **Rate limits are real and undocumented.** Hence the cache and the daily cap.

7. **Free-tier cold starts.** Render sleeps idle services, so the first request
   after a quiet period is slow.

8. **No authentication or rate limiting on the API itself.** `/v1` exists but has
   no auth middleware, and `TMR01` is catalogued but nothing enforces a per-IP
   limit yet. The daily scrape budget is what protects the account today.

9. **Not for bulk harvesting.** Single-profile, on-demand, deliberately capped.

**Legal note:** scraping LinkedIn while logged in is against LinkedIn's User
Agreement, and the account carries a genuine risk of restriction. This project
was built for a technical assignment that explicitly permits using your own
credentials. Use a throwaway account.
